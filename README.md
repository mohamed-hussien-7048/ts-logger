#  T.S Logger System — لربط جهاز البصمة   

> **نظام ربط أجهزة البصمة المتوافقة مع ZKTeco باستخدام Node.js وSQLite**  
> مشروع هدفه استقبال سجلات الحضور، حفظها في قاعدة بيانات محلية، وإرسال تحديثات للواجهة عن طريق Socket.IO — بخطوات واضحة وتنظيم أنضف للكود.

---

## ☕ الحكاية في كلمتين (Overview)

السيرفر بيعمل اتصال بجهاز البصمة لما الواجهة تبعت له عنوان الـ IP والـ Port. بعد الاتصال، بيحمّل بيانات الموظفين وسجلات الحضور الموجودة على الجهاز، وبعدها يحاول استقبال البصمات الجديدة لحظيًا، مع متابعة احتياطية (Polling) كل فترة محددة.

السجلات بتتخزن في SQLite، وقاعدة البيانات فيها قيد فريد لمنع تكرار نفس البصمة حسب الجهاز ورقم الموظف ووقت البصمة. ولما يتسجل حضور جديد، السيرفر يقدر يبعت بياناته للواجهة عن طريق Socket.IO من غير ما تحتاج تعمل Refresh.

> **مهم:** دي إعادة هيكلة أولية للكود، ولسه محتاجة اختبار تكاملي على جهاز البصمة الحقيقي ومراجعة توافقها مع الواجهة الأصلية قبل الاعتماد عليها في بيئة تشغيل فعلية.

---

## ⚡ السر في الخلطة (Key Features)

- **ربط بجهاز البصمة:** استخدام مكتبة `node-zklib` للاتصال بالجهاز.
- **تحميل الموظفين:** قراءة قائمة الموظفين من الجهاز واستخدام الاسم عند توفره.
- **مزامنة السجلات القديمة:** محاولة حفظ سجلات الحضور الموجودة بالفعل عند الاتصال.
- **استقبال لحظي:** تفعيل `getRealTimeLogs()` إذا كانت المكتبة والجهاز بيدعموها.
- **متابعة احتياطية (Polling):** فحص الجهاز دوريًا لاكتشاف زيادة عدد السجلات وقراءة السجلات عند الحاجة.
- **منع التكرار:** استخدام SQLite مع `UNIQUE(device_ip, user_id, attendance_time)` و`INSERT OR IGNORE`.
- **تحديث الواجهة:** إرسال أحداث الحالة والحضور باستخدام Socket.IO.
- **REST API:** توفير مسارات أساسية لحالة النظام وسجلات الحضور.
- **إيقاف منظم:** محاولة إغلاق اتصال الجهاز وSocket.IO وقاعدة البيانات عند إيقاف السيرفر.

## 🛠️ العدة المستخدمة (Tech Stack)

- **Node.js 18+** — بيئة تشغيل JavaScript.
- **Express.js** — مسارات HTTP وREST API.
- **Socket.IO** — التواصل اللحظي بين السيرفر والواجهة.
- **SQLite** مع `better-sqlite3` — تخزين سجلات الحضور محليًا.
- **`node-zklib`** — مكتبة الاتصال بجهاز البصمة.
- **Node.js Test Runner** — لتشغيل اختبارات الوحدة الموجودة في المشروع.

## ⚙️ ضبط الأجواء (Environment Variables)

تقدر تخصص الإعدادات عن طريق متغيرات البيئة. لو ما حددتش قيمة، السيرفر بيستخدم القيمة الافتراضية التالية:

| المتغير | القيمة الافتراضية | الفائدة |
| :--- | :--- | :--- |
| `PORT` | `5000` | بورت HTTP وSocket.IO |
| `HOST` | `0.0.0.0` | عنوان الواجهة الشبكية اللي السيرفر بيستمع عليها |
| `DATABASE_PATH` | `data/attendance.db` | مسار ملف قاعدة بيانات SQLite |
| `DEVICE_PORT` | `4370` | البورت الافتراضي لجهاز البصمة |
| `DEVICE_CONNECTION_TIMEOUT` | `10000` | مهلة الاتصال بالجهاز بالمللي ثانية |
| `DEVICE_INACTIVITY_TIMEOUT` | `4000` | مهلة عدم النشاط بالمللي ثانية |
| `POLLING_INTERVAL` | `2000` | الفترة بين محاولات المتابعة الاحتياطية بالمللي ثانية |
| `SOCKET_CORS_ORIGIN` | `*` | الـ Origin المسموح له بالاتصال عبر Socket.IO |

> إعدادات الاتصال دي موجودة في `src/config/settings.js`. قيمة `SOCKET_CORS_ORIGIN` الافتراضية `*` مناسبة للتجربة فقط؛ قيّدها قبل تشغيل الخدمة على شبكة غير موثوقة.

## 🚀 التشغيل والتجهيز (Quick Start)

### 1. المتطلبات

- تثبيت Node.js إصدار 18 أو أحدث.
- جهاز ZKTeco متوافق مع إصدار مكتبة `node-zklib` المستخدم.
- اتصال شبكي يسمح للكمبيوتر أو السيرفر بالوصول إلى عنوان IP الخاص بجهاز البصمة.

### 2. تثبيت الاعتماديات

افتح Terminal داخل فولدر المشروع ونفّذ:

```bash
npm install
```

### 3. تشغيل السيرفر

```bash
npm start
```

السيرفر بيشتغل افتراضيًا على:

- `http://localhost:5000/`
- `http://localhost:5000/api/status`

### 4. توصيل جهاز البصمة

الواجهة بتبعت حدث Socket.IO باسم `setup-device` ومعاه `ip`، وممكن تبعت `port` كمان. لو ما اتبعتش قيمة `port`، السيرفر بيستخدم `4370` افتراضيًا.

مثال للبيانات المرسلة:

```json
{
  "ip": "192.168.1.201",
  "port": 4370
}
```

عنوان IP هنا مثال فقط؛ استخدم عنوان جهازك الفعلي.

## 🌐 مسارات الـ API (HTTP API)

| Method | Endpoint | الوظيفة |
| :--- | :--- | :--- |
| `GET` | `/` | ملخص حالة السيرفر وقاعدة البيانات والجهاز |
| `GET` | `/api/status` | حالة النظام الكاملة |
| `GET` | `/api/attendance` | كل سجلات الحضور المحفوظة |
| `GET` | `/api/attendance/today` | سجلات تاريخ اليوم حسب تاريخ السيرفر المحلي |
| `GET` | `/api/attendance/date/:date` | السجلات في تاريخ محدد بصيغة `YYYY-MM-DD` |

**مثال:** `GET /api/attendance/date/2026-10-23`

> التوثيق هنا للمسارات الموجودة في نسخة إعادة الهيكلة الحالية، مش لكل المسارات اللي ممكن تكون موجودة في السيرفر القديم.

## 🔌 أحداث Socket.IO

### من الواجهة إلى السيرفر (Client → Server)

| الحدث | الوظيفة |
| :--- | :--- |
| `setup-device` | طلب الاتصال بجهاز عن طريق `ip` و`port` اختياريًا |
| `get-device-status` | طلب حالة الجهاز والنظام |
| `get-system-status` | طلب حالة النظام الحالية |
| `refresh-attendance` | طلب تشغيل فحص الحضور الاحتياطي |

### من السيرفر إلى الواجهة (Server → Client)

| الحدث | الوظيفة |
| :--- | :--- |
| `system-status` | إرسال حالة السيرفر وقاعدة البيانات والجهاز |
| `device-status` | إرسال حالة الاتصال والمراقبة للجهاز |
| `new-attendance` | إرسال سجل حضور جديد بعد حفظه بنجاح |

لازم تتم مراجعة أسماء الأحداث وشكل البيانات المرسلة ومقارنتها بالواجهة الأصلية قبل استبدال السيرفر القديم.

## 🗄️ سلامة البيانات ومنع التكرار

قاعدة البيانات بتستخدم المفتاح الفريد التالي لمنع تخزين نفس البصمة مرتين للجهاز نفسه:

```sql
UNIQUE (device_ip, user_id, attendance_time)
```

وعملية الإدخال بتستخدم `INSERT OR IGNORE`، فقاعدة البيانات نفسها بتكون خط دفاع إضافي ضد التكرار. ما تغيّرش القيد ده من غير ما تراجع طريقة تعريف السجل الفريد في النظام.

ملف قاعدة البيانات الافتراضي:

```text
data/attendance.db
```

ما ترفعش قاعدة بيانات حقيقية فيها بيانات موظفين إلى مستودع عام.

## 🧱 شكل المشروع (Project Structure)

```text
src/
├── api/
│   ├── controllers/
│   └── routes/
├── attendance/
├── config/
├── database/
├── devices/
├── realtime/
├── app.js
└── server.js

tests/
```

- `attendance/` — تنسيق بيانات الموظفين وسجلات الحضور وخدمات المعالجة.
- `config/` — إعدادات التشغيل ومتغيرات البيئة.
- `database/` — تهيئة SQLite وعمليات تخزين واسترجاع السجلات.
- `devices/` — الاتصال بالجهاز وتحميل السجلات والمراقبة الاحتياطية.
- `api/` — تعريف مسارات HTTP والتحكم في الاستجابات.
- `realtime/` — إرسال تحديثات الحضور وتجهيز حالة النظام.
- `app.js` — تجميع مكونات التطبيق وربط Express وSocket.IO.
- `server.js` — نقطة تشغيل السيرفر والتعامل مع إشارات الإيقاف.
- `tests/` — اختبارات وحدة لتنسيق الوقت وتطبيع البيانات.
